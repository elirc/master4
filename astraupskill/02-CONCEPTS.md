# 02: concepts behind safe reservation CRUD

Inventory has two related quantities. `onHand` means units physically recorded at a warehouse. `reserved` means units already promised to orders but not shipped. Available-to-promise, implemented by `availableToPromise`, is `Math.max(0, onHand - reserved)`. If a balance has 42 on hand and 20 reserved, the API can promise 22. Reserving 5 changes the reserved count to 25; shipping those 5 later reduces both on-hand and reserved. This is a domain rule, rather than a formatting detail, because it decides whether a customer order can move from `pending_reservation` to `allocated`.

A `SalesOrder` has many `SalesOrderLine` records, while an `InventoryItem` is unique for a warehouse and SKU. Suppose the same SKU appears twice with quantities 14 and 9. Each line is 14 or 9, and each is less than 22, but the order asks for 23 total. Checking lines independently treats one shared stock pool as two separate pools. The corrected planner groups by `skuId` before checking. Grouping is safe because the warehouse is fixed by the order and the balances passed to the helper represent that warehouse.

The patch also defines valid reservation input as a positive safe integer. Prisma models quantities as integers, but a plain TypeScript helper can be called by tests, imports, workers, or a future endpoint. A zero quantity is not useful work; a negative quantity would reduce `reserved`; a fraction or infinity cannot represent warehouse units. `planReservation` reports invalid lines in its normal `ReservationDecision` shape. `applyReservation` throws because it is a state transformation and cannot return a meaningful balance after an invalid mutation. It also rejects a quantity larger than available stock, giving direct protection to callers that skip planning.

These checks do not replace the transaction in `orders.service.ts`. The service still reads, plans, updates, and writes audit/event/outbox records together. The shared helper makes the decision deterministic and reusable; the transaction makes the multi-record workflow atomic. Keeping those responsibilities separate is the useful design lesson: pure rules are easy to test, while orchestration owns persistence boundaries.
