# 02: concepts behind safe reservation CRUD

Inventory has two related quantities. `onHand` means units physically recorded at a warehouse. `reserved` means units already promised to orders but not shipped. Available-to-promise, implemented by `availableToPromise`, is `Math.max(0, onHand - reserved)`. If a balance has 42 on hand and 20 reserved, the API can promise 22. Reserving 5 changes the reserved count to 25; shipping those 5 later reduces both on-hand and reserved. This is a domain rule, rather than a formatting detail, because it decides whether a customer order can move from `pending_reservation` to `allocated`.

The clamp to zero is a deliberate choice with a cost. If bad data ever leaves `reserved` above `onHand` (say 5 on hand, 20 reserved), `availableToPromise` reports 0 and `stockHealth` reports `'stockout'`, which looks like an ordinary empty shelf. The 15 units of over-promise are invisible on the dashboard. Practice exercise 4 pins this behavior.

A `SalesOrder` has many `SalesOrderLine` records, while an `InventoryItem` is unique for a warehouse and SKU. Suppose the same SKU appears twice with quantities 14 and 9. Each line is less than 22, but the order asks for 23 total. Checking lines independently treats one shared stock pool as two separate pools. The corrected planner groups by `skuId` before checking. Grouping by SKU alone is safe only because the caller passes balances for one warehouse: `reserveSalesOrder` filters by `order.warehouseId` (`orders.service.ts:51-56`). `planReservation` itself looks balances up with `balances.find` on `skuId` only, so a caller that mixed warehouses would get whichever row came first (exercise 6).

The patch also defines valid reservation input as a positive safe integer (`Number.isSafeInteger(q) && q > 0`). Prisma models quantities as integers, but a plain TypeScript helper can be called by tests, imports, workers, or a future endpoint. A zero quantity is not useful work; a negative quantity would reduce `reserved`; a fraction, `NaN` or infinity cannot represent warehouse units. `planReservation` reports invalid lines in its normal `ReservationDecision` shape. `applyReservation` throws because it is a state transformation and cannot return a meaningful balance after an invalid mutation. It also rejects a quantity larger than available stock, giving direct protection to callers that skip planning.

Planning and applying are two separate checks, and the service uses both. `planReservation` produces the decision the API reports back. Then, inside the write loop, `applyReservation(balance, quantity)` (`orders.service.ts:93`) re-checks each per-SKU total against the balance that was read; if it throws, the whole transaction rolls back. The write loop also aggregates by SKU (`:77-80`), so an order with two lines for one SKU produces one `InventoryItem` increment and one `StockReservation` row whose quantity is the sum.

Neither check replaces the transaction in `orders.service.ts`. The service reads, plans, updates, and writes event, outbox and audit records together. The shared helper makes the decision deterministic and reusable; the transaction makes the multi-record workflow atomic. Note what neither gives you: both checks compare against the `balances` read at the start of the transaction, and the `reserved: { increment }` update at `:95-98` is unconditional. Whether two concurrent reservations of the same SKU can both pass depends on the database's isolation, not on this code (see F3 in `06`).
