# 01: codebase map and reading order

Atlas Fulfillment is intentionally a modular monolith. The browser code in `src/App.tsx` asks the client API in `src/client/api.ts` for dashboard-shaped data. `src/server/app.ts` composes Express routes and middleware. The route for `POST /api/orders/:orderId/reserve` checks the role and calls `reserveSalesOrder` in `src/server/modules/orders/orders.service.ts`. That service opens a Prisma transaction, reads the order and its lines, reads inventory for the order warehouse, invokes `planReservation`, and only then writes `InventoryItem`, `StockReservation`, `SalesOrder`, `DomainEvent`, `OutboxMessage`, and `AuditLog` records. The browser therefore sees a result produced by several layers, even though the business decision is a plain shared function.

Read `prisma/schema.prisma` next. `SalesOrderLine.quantity` is an integer, and `InventoryItem` has one row per `(warehouseId, skuId)` because of its compound unique constraint. That relationship is the key evidence for the bug: repeated order lines still refer to one inventory row. Read `src/shared/inventoryRules.ts` after the schema. `availableToPromise` computes `onHand - reserved` and clamps negative results to zero. `planReservation` decides whether all requested units fit. `applyReservation` is a pure state transformation, while `applyShipment` protects the reserved quantity when shipping.

The tests in `tests/inventoryRules.test.ts` are the fastest feedback loop. They create an in-memory object called `balance`, so they test the domain rule without a database. `tests/api.test.ts` covers health, dashboard, and CSV routes, but it is not the right first place for this fix because it exercises seeded persistence. A useful reading order is: schema, shared rules, domain tests, order service, API route, then client. This order moves from invariant to orchestration to transport. It also prevents a common junior mistake: changing a UI quantity check when the server-side rule is the actual protection boundary.

When tracing a future CRUD change, write down the input type, the owner of the invariant, the persistence mutation, and the observable response. For this change those are `ReservationLine[]`, `inventoryRules.ts`, the transaction updates in `orders.service.ts`, and `ReservationResultDto`. That small map is enough to keep the patch focused.
